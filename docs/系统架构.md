# 系统架构

OfferMate AI 采用前后端分离架构。前端负责页面展示和交互，后端提供 REST API 与 WebSocket 通信能力，核心数据存储在 MySQL，缓存、异步消息、搜索、文件存储和 AI 能力由独立基础设施支撑。

## 总体架构

```text
┌────────────────────────────┐
│        Vue3 PC Web          │
│  Vite / Element Plus        │
└──────────────┬─────────────┘
               │ HTTP / WebSocket
┌──────────────▼─────────────┐
│     Spring Boot Backend     │
│ Controller / Service / DAO  │
└──────┬──────┬──────┬───────┘
       │      │      │
       │      │      ├──────────── MinIO
       │      │      │             文件对象存储
       │      │
       │      ├────────────────── Elasticsearch
       │      │                    岗位全文搜索
       │
       ├───────────────────────── Redis
       │                          缓存 / 限流 / 黑名单 / 锁
       │
       ├───────────────────────── RabbitMQ
       │                          异步通知 / AI 日志
       │
       ├───────────────────────── MySQL
       │                          核心业务数据
       │
       └───────────────────────── 智谱 AI (ZhipuAI)
                                  Spring AI (ChatModel / VectorStore / ChatMemory)
```

## 后端分层

后端代码包名以 `com.offermate` 为根包，整体采用经典三层结构：

```text
controller  接口层，负责接收请求和返回 Result
service     业务层，负责业务规则、权限校验、事务控制
mapper      数据访问层，基于 MyBatis-Plus 操作数据库
entity      数据库实体
dto         请求参数对象
vo          返回视图对象
config      Redis、MQ、ES、MinIO、WebSocket、Spring AI 等配置
interceptor JWT 登录拦截器
websocket   聊天 WebSocket 处理
aspect      AOP 操作日志
exception   统一业务异常
common      通用结果集与常量
```

## 数据流向

典型请求流程：

```text
1. 用户在前端触发操作
2. 请求携带 Authorization: Bearer <token>
3. JwtInterceptor 校验 Token，将当前用户信息存入 UserContext (ThreadLocal)
4. Controller 接收 DTO 并进行 JSR-303 参数校验
5. Service 执行业务逻辑：
   - 权限判断（Seeker / Recruiter / Admin）
   - Redis 防重 / 限流 / 缓存查询
   - MySQL 增删改查
   - Elasticsearch 搜索同步
   - RabbitMQ 发送异步通知与日志
   - Spring AI 原生调用智谱 GLM-4 / Embedding-3 大模型
6. 返回统一 Result 结构
7. 拦截器 afterCompletion 清理 ThreadLocal
```

## 缓存架构（Redis）

Redis 在系统中主要承担以下职责：

1. **Token 黑名单**：用户登出后，将 Token 放入 Redis，设置与 Token 剩余有效期一致的过期时间。
2. **岗位详情缓存**：对高频访问的岗位详情进行缓存，更新/删除时失效缓存。
3. **防重复投递**：`SET key val NX EX` 保证同一求职者对同一岗位短时间内无法重复投递。
4. **AI 限流**：按用户 ID 统计每日 AI 调用次数，超出限额直接拦截。
5. **聊天未读数**：维护用户未读消息统计，加速前端角标拉取。

## 消息队列架构（RabbitMQ）

采用 Direct Exchange 路由，解耦核心业务与耗时/次要逻辑：

1. **投递通知队列**：求职者投递后，异步写入企业招聘者通知中心。
2. **面试邀请队列**：企业发送面试邀请后，异步写入求职者通知中心。
3. **企业审核队列**：管理员审核企业资质后，异步通知招聘者。
4. **AI 调用日志队列**：异步写入 `ai_call_log` 表，避免日志持久化阻塞 AI 响应。

## 搜索架构（Elasticsearch）

1. **索引设计**：`job_position` 索引，包含岗位标题、城市、薪资范围、学历、经验、技能标签、岗位描述、公司信息。
2. **分词器**：支持 ik_max_word / ik_smart 中文分词。
3. **同步机制**：岗位发布/修改/下架时同步更新 ES；支持管理端全量重建同步接口。

## 对象存储（MinIO）

1. 用户头像存储
2. 企业 Logo 存储
3. 简历附件预留存储

## WebSocket 聊天架构

WebSocket 地址：

```text
/ws/chat?token=jwt-token
```

握手阶段通过 token 识别用户身份。后端维护在线用户连接，发送文本消息时：

1. 校验会话是否存在。
2. 校验发送人和接收人是否为会话参与者。
3. 消息落库。
4. 更新会话最后一条消息。
5. 如果接收人在线，实时推送。
6. 更新接收方未读数。

## AI 架构

项目全面采用 Spring AI 官方框架原生接入智谱 AI（Zhipu AI）：

- **大模型核心**：对话模型使用 `glm-4-flash`，向量模型使用 `embedding-3` (1024 维)。
- **单轮生成业务**：简历优化、表单优化、分模块优化、面试题生成、岗位描述生成（通过 `ChatModel` 原生调用）。
- **模拟面试与岗位匹配**：
  - `AiInterviewService`：岗位匹配度多维度分析打分、模拟面试报告生成。
  - `InterviewAssistant`：模拟面试官多轮出题、回答打分与深度追问。
  - `RagConfig` / `PgVectorStore`：基于 Spring AI 原生 `SentenceTextSplitter` 进行标点符号短句切分，结合 `TikaDocumentReader` 读取题库并持久化向量索引至 PostgreSQL **pgvector** 向量数据库（HNSW 索引，1024 维，Cosine 相似度）。
  - `PersistentChatMemory`：实现 Spring AI `ChatMemory` 接口，构建**双层会话记忆架构**：
    - **短期记忆（Redis）**：实时多轮问答超低延迟读写与 TTL 自动续期。
    - **长期记忆（MySQL）**：全量持久化归档至 `ai_chat_memory` 表，支持 Cache-Aside 自动回填。
- **Spring AI 工具调用（Tool / Function Calling）**：
  - `OfferMateAiTools`：大模型通过 `@Tool` 与 Spring AI Function 回调自主触发平台业务工具：
    - `queryJobRequirements`：根据关键词查询正在招聘的真实岗位详情与技能要求。
    - `queryCompanyBackground`：查询企业背景、规模、行业与认证资质。
    - `querySalaryBenchmark`：查询特定城市与岗位的行业薪酬行情基准与谈薪策略。
    - `evaluateSkillMatch`：计算候选人技能与岗位要求的匹配率并给出缺失技能追问建议。

AI 调用统一做：

- 权限校验
- Redis 每日限流
- Prompt 长度限制
- 异常兜底
- RabbitMQ 异步调用日志记录
